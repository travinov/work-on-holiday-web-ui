# Процессы сотрудника и администратора

Документ описывает рабочие сценарии Web UI для оформления выхода в выходной день, фиксации факта и административного закрытия периодов. Процесс согласования выхода выполняется вне системы; Web UI фиксирует заявки, фактически отработанное время, блокировки и отчеты.

## Роли

| Роль | Что делает в системе | Что делает вне системы |
| --- | --- | --- |
| Сотрудник | Регистрируется/входит, создает заявки, корректирует их до принятия в работу, отменяет заявки до принятия в работу, указывает факт после выполнения работ. | Согласует выход по принятому в организации процессу. Если период закрыт и нужна правка, связывается с администратором. |
| Администратор | Управляет пользователями, формирует отчеты, закрывает прием заявок, закрывает ввод факта, меняет статусы заявок, корректирует заявки после блокировок, перевыпускает токены. | Заводит заявки во внешних системах, получает обращения от сотрудников по правкам после закрытия. |
| Суперпользователь | Входит по логину/паролю релизной конфигурации, назначает администраторов и выполняет админские операции. | Используется для первичной настройки и аварийного доступа. |

## Статусы и блокировки

### Статусы заявки

| Статус | UI-текст | Значение | Кто переводит |
| --- | --- | --- | --- |
| `active` | Заявка подана | Сотрудник создал заявку. Плановая часть еще может быть скорректирована сотрудником, если нет блокировок. | Система при создании; администратор при возврате на корректировку. |
| `in_progress` | Принята в работу | Администратор зафиксировал плановую часть. Сотрудник видит, что заявка принята, но еще не закрыта по факту. | Администратор при `Закрыть прием заявок`. |
| `in_fact` | Факт указан | Сотрудник указал фактическую дату и время. Администратор еще не закрыл факт. | Сотрудник или администратор при сохранении факта. |
| `completed` | Закрыта | Заявка окончательно закрыта после проверки/закрытия факта. | Администратор при `Закрыть ввод факта` или ручной сменой статуса. |
| `cancelled` | Отменена | Заявка отменена. | Сотрудник только из `active`; администратор вручную из любого статуса при необходимости. |

Отметка `заявка откорректирована` не является отдельным статусом. Она ставится, когда меняются плановые поля заявки: дата, время, условия выхода, задача, обоснование или АС.

### Статусная модель

```mermaid
stateDiagram-v2
    [*] --> active: Заявка создана

    active --> active: Сотрудник корректирует план
    active --> cancelled: Сотрудник отменяет до закрытия приема
    active --> in_progress: Администратор закрывает прием заявок

    in_progress --> active: Администратор возвращает на корректировку
    in_progress --> in_fact: Сотрудник указывает факт
    in_progress --> cancelled: Только администратор

    in_fact --> in_fact: Факт исправлен до закрытия факта
    in_fact --> completed: Администратор закрывает ввод факта
    in_fact --> in_progress: Администратор возвращает факт на исправление
    in_fact --> cancelled: Только администратор

    completed --> in_fact: Только администратор при ошибке факта
    completed --> active: Только администратор при полном откате
    completed --> cancelled: Только администратор аварийно
```

### Блокировки периода

| Блокировка | Что делает | Что запрещает сотруднику | Что может администратор |
| --- | --- | --- | --- |
| `Закрыть прием заявок` (`planning`) | Создает блокировку периода и переводит `active` заявки выбранного периода в `in_progress`. | Создание, отмену и корректировку плановой части заявки за выбранный период. | Создавать, отменять, корректировать заявки и вручную менять статус в админ-режиме; снять блокировку приема без отката статусов. |
| `Закрыть ввод факта` (`actual`) | Создает блокировку периода и переводит заявки `in_fact` с фактической датой в периоде в `completed`. | Ввод и изменение фактически отработанного времени за выбранный период. | Вносить/исправлять факт и вручную менять статус в админ-режиме. |
| Закрытие отчетом (`app_report_lock`) | Фиксирует заявки, попавшие в сформированный отчет. | Самостоятельные правки по заявкам из отчета. | Корректировать в админ-режиме при необходимости. |

Снятие блокировки `planning` удаляет только запись блокировки. Статусы заявок не откатываются автоматически: `in_progress` остается `in_progress`, пока администратор вручную не вернет конкретную заявку в `active`. Возврат в `active` открывает сотруднику плановую корректировку только по этой заявке и не снимает блокировку со всего периода.

## Общая схема процесса

```mermaid
flowchart TD
    A["Начало недели или период планирования"] --> B["Сотрудник входит в кабинет"]
    B --> C{"Пользователь уже зарегистрирован?"}
    C -- "Нет" --> D["Система создает профиль, сохраняет признак Грейд 12+ и показывает токен один раз"]
    C -- "Да" --> E["Сотрудник вводит токен"]
    D --> F["Сотрудник создает одну или несколько заявок"]
    E --> F
    F --> G["Заявка получает статус active"]
    G --> H["Согласование выхода проходит вне системы"]
    H --> I{"Администратор закрыл прием заявок?"}
    I -- "Нет" --> J["Сотрудник может корректировать или отменять заявку"]
    J --> F
    I -- "Да" --> K["Заявка переходит в in_progress"]
    K --> L["Плановые правки сотруднику недоступны"]
    L --> M["Сотрудник выходит и выполняет работы"]
    M --> N["Сотрудник указывает фактическую дату и время"]
    N --> O["Заявка переходит в in_fact"]
    O --> P["Администратор проверяет факт и формирует отчетность"]
    P --> Q["Администратор закрывает ввод факта"]
    Q --> R["Заявка переходит в completed"]
```

## Workflow сотрудника

### 1. Первый вход или повторный вход

```mermaid
flowchart TD
    A["Открыть главную страницу"] --> B["Перейти в кабинет сотрудника"]
    B --> C["Ввести полное ФИО"]
    C --> D{"ФИО найдено в системе?"}
    D -- "Нет" --> E["Указать чекбокс Грейд 12+ при необходимости"]
    E --> F["Система регистрирует пользователя"]
    F --> G["Система показывает персональный токен один раз"]
    G --> H["Сотрудник сохраняет токен безопасно"]
    D -- "Да" --> I{"Токен уже выдан?"}
    I -- "Нет" --> G
    I -- "Да" --> J["Ввести токен"]
    J --> K{"Токен корректный?"}
    K -- "Да" --> L["Открывается личный кабинет"]
    K -- "Нет или потерян" --> M["Нажать Забыл токен"]
    M --> N["Администратор видит отметку и перевыпускает токен"]
```

Правила:

- ФИО вводится полностью без сокращений.
- Токен показывается один раз. После этого сотрудник входит по ФИО и токену.
- Если токен потерян, сотрудник нажимает `Забыл токен`; администратор перевыпускает токен и передает его сотруднику безопасным способом.
- Если пользователь заблокирован или архивирован, вход недоступен до изменения статуса администратором.

### 2. Создание заявки

```mermaid
flowchart TD
    A["Открыт кабинет сотрудника"] --> B["Нажать Создать новую заявку"]
    B --> C["Заполнить плановую дату"]
    C --> D["Заполнить плановое время"]
    D --> E{"Грейд 12+?"}
    E -- "Да" --> F["Доступны только условия выхода: Отгул"]
    E -- "Нет" --> G["Доступны: Отгул или Двойная оплата"]
    F --> H["Заполнить задачу"]
    G --> H
    H --> I["Заполнить обоснование"]
    I --> J["Указать АС: после каждой АС нажать Enter или Tab"]
    J --> K{"Дата попадает в закрытый прием заявок?"}
    K -- "Нет" --> L["Система создает заявку со статусом active"]
    K -- "Да" --> M["Создание запрещено. Нужно обратиться к администратору"]
```

Правила:

- На каждый независимый временной слот создается отдельная заявка.
- Если сотрудник работает в субботу и воскресенье, создаются две заявки, по одной на каждую дату.
- Если в один день есть два разных временных окна, создаются две заявки на одну дату с разным временем.
- Для сотрудников с признаком `Грейд 12+` значение `Двойная оплата` недоступно.

### 3. Корректировка или отмена заявки

```mermaid
flowchart TD
    A["Сотрудник раскрывает заявку"] --> B{"Статус active и нет блокировки planning/report?"}
    B -- "Да" --> C["Можно изменить плановую дату, время, условия, задачу, обоснование, АС"]
    C --> D["Сохранить корректировку"]
    D --> E["Система ставит отметку заявка откорректирована"]
    B -- "Да, заявка больше не нужна" --> F["Нажать Перевести в статус Отменена"]
    F --> G["Заявка получает статус cancelled"]
    B -- "Нет" --> H["Форма корректировки недоступна"]
    H --> I["Если правка нужна, сотрудник пишет администратору"]
    I --> J["Администратор возвращает заявку в active или правит сам"]
```

Правила:

- Сотрудник может корректировать или отменять только заявку в статусе `active`.
- После `Закрыть прием заявок` заявка становится `in_progress`, и плановые действия сотруднику недоступны.
- Если после закрытия приема обнаружена ошибка в заявке, сотрудник обращается к администратору. В системе это не автоматизированное согласование.
- Администратор может вручную вернуть заявку `in_progress -> active`; это открывает сотруднику корректировку конкретной заявки даже при сохраненной общей блокировке приема. Альтернатива: администратор вносит правку сам в админ-режиме.

### 4. Ввод фактически отработанного времени

```mermaid
flowchart TD
    A["Работы выполнены"] --> B["Сотрудник раскрывает соответствующую заявку"]
    B --> C{"Статус in_progress или in_fact?"}
    C -- "Нет" --> D["Факт недоступен"]
    C -- "Да" --> E{"Ввод факта за дату закрыт?"}
    E -- "Нет" --> F["Указать фактическую дату"]
    F --> G["Указать фактическое время"]
    G --> H["Сохранить факт"]
    H --> I["Заявка получает статус in_fact"]
    E -- "Да" --> J["Сотрудник обращается к администратору"]
```

Правила:

- Сотрудник указывает факт только по заявке `in_progress` или исправляет факт по заявке `in_fact`, если факт не закрыт.
- Закрытие приема заявок не запрещает ввод факта.
- Ввод факта запрещает только `Закрыть ввод факта` или закрытие заявки отчетом.
- Если работа шла через границу суток, используется нормализованная фактическая дата и время по правилам отчета.

## Workflow администратора

### 1. Подготовка пользователей

```mermaid
flowchart TD
    A["Администратор входит как пользователь с ролью администратора или суперпользователь"] --> B["Открыть Пользователи"]
    B --> C["Проверить список сотрудников"]
    C --> D["При необходимости изменить Грейд 12+"]
    D --> E["При необходимости назначить/снять роль администратора"]
    E --> F["При необходимости изменить статус: Активен, Заблокирован, Архив"]
    F --> G["При потере токена перевыпустить токен"]
```

Правила:

- `Заблокирован` и `Архив` делают вход сотрудника недоступным.
- При архивировании активные незакрытые заявки могут быть отменены системой, если они не находятся в закрытом периоде.
- Токен передается сотруднику вне системы безопасным способом.

### 2. Еженедельная подготовка заявок

```mermaid
flowchart TD
    A["В течение недели сотрудники создают заявки active"] --> B["Администратор открывает Заявки"]
    B --> C["Проверяет состав заявок, даты, время, условия, задачи, АС"]
    C --> D{"Есть ошибки до закрытия приема?"}
    D -- "Да" --> E["Сотрудник корректирует сам или администратор корректирует в админ-режиме"]
    D -- "Нет" --> F["Администратор формирует плановый Excel за выбранную неделю"]
    E --> F
    F --> G["Администратор заводит заявки во внешних системах"]
    G --> H["Администратор выполняет Закрыть прием заявок"]
    H --> I["Заявки active за период переходят в in_progress"]
```

Правила:

- Отчет формируется за выбранную неделю/период.
- `Закрыть прием заявок` фиксирует плановую часть для сотрудников и переводит `active -> in_progress`.
- Существующие заявки не удаляются.
- Если блокировка приема была поставлена ошибочно, администратор может снять ее кнопкой `Снять прием`; статусы заявок при этом не откатываются.
- Если конкретную заявку нужно вернуть сотруднику на правку, администратор вручную переводит ее `in_progress -> active`; остальные заявки периода остаются заблокированными.

### 3. После выполнения работ

```mermaid
flowchart TD
    A["Сотрудники выходят и выполняют работы"] --> B["Сотрудники вводят факт по in_progress заявкам"]
    B --> C["Заявки получают статус in_fact"]
    C --> D["Администратор проверяет заявки со статусом in_fact"]
    D --> E{"Все сотрудники внесли факт?"}
    E -- "Нет" --> F["Связаться с сотрудниками вне системы или внести факт в админ-режиме"]
    F --> D
    E -- "Да" --> G["Сформировать общий Excel с отчетами 1-4"]
    G --> H["Передать/использовать отчет для закрытия во внешних системах"]
    H --> I["Выполнить Закрыть ввод факта"]
    I --> J["Заявки in_fact за период переходят в completed"]
```

Правила:

- `in_fact` означает, что сотрудник уже отчитался, но администратор еще не закрыл итоговый процесс.
- `Закрыть ввод факта` применяется после того, как факт собран и проверен.
- После закрытия факта сотрудник не может изменить фактическую дату или время.
- Администратор может внести исправление в админ-режиме, если есть обоснованная необходимость.

## Corner cases

### Несколько заявок одного сотрудника

| Ситуация | Как оформлять |
| --- | --- |
| Сотрудник работает в субботу и воскресенье | Две заявки: одна на субботу, одна на воскресенье. |
| Сотрудник работает в один день в двух разных окнах | Две заявки на одну дату с разным временем. |
| Сотрудник меняет время до закрытия приема | Сотрудник раскрывает заявку `active` и сохраняет корректировку. |
| Сотрудник меняет время после закрытия приема | Сотрудник обращается к администратору; администратор возвращает заявку в `active` или правит сам. |

### Закрытый прием заявок

| Ситуация | Поведение системы |
| --- | --- |
| Создание новой заявки сотрудником на закрытую дату | Запрещено. |
| Закрытие приема заявок | `active` заявки выбранного периода переходят в `in_progress`. |
| Корректировка `in_progress` заявки сотрудником | Запрещено, даже если блокировку приема потом сняли. |
| Перенос закрытой заявки сотрудником на открытую дату через прямой POST | Запрещено backend-проверкой. |
| Отмена `in_progress` заявки сотрудником | Запрещено. |
| Ввод факта сотрудником по `in_progress` заявке | Разрешен, если не закрыт ввод факта. |
| Админская корректировка закрытой заявки | Разрешена в админ-режиме. |
| Администратор снимает блокировку приема | Удаляется только запись блокировки `planning`; статусы `active`, `in_progress`, `in_fact`, `completed`, `cancelled` и отметки корректировок не меняются. |

### Закрытый ввод факта

| Ситуация | Поведение системы |
| --- | --- |
| Закрытие ввода факта | `in_fact` заявки с фактической датой в выбранном периоде переходят в `completed`. |
| Сотрудник пытается ввести факт после закрытия факта | Запрещено. |
| Сотрудник ошибся в факте после закрытия факта | Обращается к администратору. |
| Администратор правит факт после закрытия факта | Разрешено в админ-режиме. |

### Пользователи и токены

| Ситуация | Поведение системы |
| --- | --- |
| Новый сотрудник входит впервые | Система создает профиль и показывает токен один раз. |
| Сотрудник потерял токен | Нажимает `Забыл токен`; администратор перевыпускает токен. |
| Токен ввели неверно | Вход не выполняется. |
| Пользователь заблокирован или архивирован | Вход запрещен. |
| Изменился признак `Грейд 12+` | Администратор меняет признак в пользователях. В новых/корректируемых заявках меняется доступность `Двойная оплата`. |

### Отчеты

| Ситуация | Поведение системы |
| --- | --- |
| Отчет сформирован до ввода факта | Плановые листы содержат заявки, фактические данные могут быть пустыми. |
| Факт внесен после отчета | Нужно сформировать отчет повторно, если руководству нужен актуальный файл. |
| Заявка отменена | В отчетах учитывается согласно текущей логике статуса; администратор должен проверять статус перед внешним закрытием. |
| Нет заявок за выбранную неделю | Отчет может быть пустым по соответствующим листам. |

## Коммуникация после блокировки

Если сотруднику нужна правка после административной блокировки:

1. Сотрудник не меняет данные в системе самостоятельно.
2. Сотрудник направляет администратору письмо или сообщение в корпоративном канале.
3. В обращении указывает ФИО, дату заявки, плановое время, что нужно изменить и причину изменения.
4. Администратор проверяет, допустима ли правка после закрытия периода.
5. Администратор возвращает заявку в `active`, вносит изменение сам в админ-режиме или отказывает с пояснением.
6. Если правка влияет на уже сформированный отчет, администратор формирует новый Excel и использует актуальную версию.

Рекомендуемый шаблон обращения:

```text
Тема: Правка заявки на выход в выходной после закрытия периода

ФИО:
Дата заявки:
Текущее плановое время:
Что нужно изменить:
Причина изменения:
Нужно ли менять фактически отработанное время:
```

## Открытые вопросы

Эти правила стоит уточнить перед промышленным использованием:

1. Нужен ли отдельный фиксированный e-mail администратора для обращений после блокировки или достаточно корпоративного канала?
2. Нужно ли хранить историю админских правок после закрытия периода отдельным audit log?
3. Должен ли отчет исключать `cancelled` заявки или показывать их отдельной отметкой?
4. Нужно ли автоматически закрывать прием заявок сразу после формирования Excel или администратор должен закрывать период отдельной кнопкой?

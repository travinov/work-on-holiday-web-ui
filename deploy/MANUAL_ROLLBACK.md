# Подготовка к обновлению и ручной откат

## Что сделать перед новой сборкой

1. Распаковать новую сборку на корпоративном компьютере и открыть Terminal в её папке. Использовать скрипты именно этой сборки: в старом скрипте сохранялась только БД.
2. Для уже установленного текущего экземпляра запустить `deploy/scripts/update-corporate-server.sh`. Для отдельно проверенной Production-сборки — `deploy/scripts/update-production-corporate-server.sh`. Скрипты `install-*` предназначены только для первой установки.
3. Дождаться сообщения `Restore point verified: <полный путь>`. Сохранить этот путь вместе с журналом обновления. Если резервное копирование или проверка не удались, скрипт завершится до rsync и не начнёт замену версии.

Отдельно сохранять предыдущий ZIP не обязательно: предыдущая версия берётся с сервера **до** копирования новых файлов. Нужны права чтения штатных файлов приложения и записи в каталог резервных копий, а также место для архива приложения с `venv`, снимка БД, SQL-dump и его временного восстановления. Комплекты не удаляются автоматически. Не публиковать их: они содержат настройки с секретами и данные сотрудников.

Это подготовка к ручному откату на том же сервере и по тем же путям. Автоматического отката нет. Проверка комплекта не заменяет проверку запуска восстановленной версии на целевом сервере.

## Что сохраняется

Текущий экземпляр: `~/.local/state/work-on-holiday/backups/restore-points/`.
Production: `~/.local/state/work-on-holiday-production/backups/restore-points/`.
В каждом создаётся отдельная папка `pre-update-<дата-время-UTC>-<идентификатор>`.

| Файл | Назначение |
| --- | --- |
| `application.tar.gz` | Предыдущий код, шаблоны, скрипты и установленный `venv`; корень архива — `application/` |
| `database.sqlite` | Согласованный снимок БД через SQLite Backup API, включая данные из WAL |
| `database.sql` | SQL-dump того же снимка; восстановление во временную БД проверяется перед обновлением |
| `application.env` | Настройки экземпляра |
| `start.sh`, `watchdog.sh` | Прежние скрипты запуска и перезапуска |
| `crontab-reference.txt` | Справочная копия crontab; не предназначена для замены всего текущего crontab |
| `manifest.json` | Пути, экземпляр, сервис, порт, версия Python, размеры и SHA-256 файлов |
| `README.txt` | Краткая последовательность ручного восстановления |

Из архива приложения исключены `.git`, отчёты, выгрузки, резервные копии, служебные результаты проверок и кеш Python. Эти данные не удаляются обновлением; при ручной замене каталога приложения их нужно сохранить отдельно и вернуть на место. Системный Python и ОС не архивируются. Сохранённый `venv` восстанавливается по прежнему абсолютному пути на том же сервере без переустановки зависимостей.

Проверить комплект повторно можно без восстановления, запустив на сервере helper из новой сборки:

```bash
python3 /путь/к/новой/сборке/deploy/scripts/create-restore-point.py \
  --verify /полный/путь/к/комплекту
```

## Если понадобится откат

Порядок относится к штатному запуску через `screen` и `crontab` watchdog. Конкретные пути брать из выбранного `manifest.json`; для Production использовать его собственные пути и порт. Если запуск настроен иначе, сначала установить фактический способ запуска и автоперезапуска.

1. Выбрать комплект, проверить его целостность. Скопировать его за пределы каталога приложения, если резервные копии размещены внутри него. Убедиться, что системный Python, на который ссылается сохранённый `venv`, доступен.
2. Сохранить текущее состояние отдельно: текущий код, `venv`, env, скрипты запуска и согласованную копию БД. Это сохранит заявки и изменения, появившиеся после обновления. Не перезаписывать выбранный комплект отката.
3. Сохранить текущий crontab. Временно убрать **только** записи запуска и watchdog нужного экземпляра. Не заменять весь crontab старой копией: это может затронуть другие приложения и второй контур.
4. Остановить соответствующую `screen`-сессию; если есть активный `systemd --user` сервис или другой автозапуск этого экземпляра, остановить и его. Проверить отсутствие процесса приложения и слушателя на его порту. Перед заменой БД сохранить окончательный снимок остановленной базы, чтобы не потерять записи между шагами 2 и 4.
5. Сохранить текущую папку приложения под отдельным именем. Из `application.tar.gz` восстановить прежние файлы вместе с `venv` в **исходный абсолютный путь** `app_dir`. Не накладывать архив поверх новой версии: иначе останутся новые файлы. Вернуть отдельно сохранённые отчёты и другие исключённые рабочие каталоги, если они нужны.
6. Восстановить `application.env` по пути `env_file` и скрипты `start.sh`/`watchdog.sh` по путям из `runtime_files`. Поставить env права `600`, скриптам — право исполнения для владельца. Не выводить содержимое env в терминал или журнал.
7. Для полного возврата к состоянию до обновления восстановить `database.sqlite` по пути `db_path`. Перед заменой сохранить текущую БД вместе с существующими файлами `-wal`, `-shm` и `-journal` отдельно; старые побочные файлы не должны оставаться рядом с восстановленной БД. Вернуть БД владельца приложения и ограниченные права доступа. **В снимке не будет изменений после его создания.**
8. Запустить сохранённый start-скрипт, проверить HTTP-ответ, вход, список заявок и отчётность. После успешной проверки вернуть только соответствующие записи запуска и watchdog в текущий crontab и проверить их работу. Не запускать обычный update/deploy поверх восстановления: он переустанавливает зависимости и выполняет инициализацию схемы.

Возврат только кода с сохранением текущей БД возможен лишь после проверки совместимости. Новая сборка включает реестр сотрудников и руководителей; после его импорта совместимость со старой схемой идентификации нельзя считать подтверждённой автоматически.

## Границы проверки

Локальные тесты проверяют сохранение и восстановление содержимого предыдущей версии и данных, контроль повреждённых копий, сохранность истории и прекращение обновления до rsync при ошибке резервного копирования. Команды SSH и rsync в тестах подменены; это не проверка отката на корпоративном сервере. Создание снимка не останавливает работающий сервер: при откате возвращается состояние БД на момент снимка, а не на момент последующего перезапуска приложения.
